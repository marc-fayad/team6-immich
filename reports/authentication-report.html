19. Weak Credential Transit  [State: Not Started]  [Priority: High] 

Category:Information Disclosure
Description:Credentials on the wire are often subject to sniffing by an attacker. Are the credentials re-usable/re-playable? Are credentials included in a message? For example, sending a zip file with the password in the email. Use strong cryptography for the transmission of credentials. Use the OS libraries if at all possible, and consider cryptographic algorithm agility, rather than hardcoding a choice.
Justification:The modeled reverse proxy forwards authentication and session requests to the Immich server over HTTP. If credentials or reusable session tokens are transmitted across this connection, an attacker with access to the internal network could intercept and potentially replay them. Recommended mitigations include TLS for internal traffic where supported, network isolation, restricted access between components, and secure session management. These protections require deployment and implementation verification before the threat can be considered mitigated.

40. Potential SQL Injection Vulnerability for PostgreSQL (Users & Sessions)  [State: Not Started]  [Priority: High] 

Category:Tampering
Description:SQL injection is an attack in which malicious code is inserted into strings that are later passed to an instance of SQL Server for parsing and execution. Any procedure that constructs SQL statements should be reviewed for injection vulnerabilities because SQL Server will execute all syntactically valid queries that it receives. Even parameterized data can be manipulated by a skilled and determined attacker.
Justification:SQL injection is a potential threat because authentication and session management require database operations involving user-related input. If untrusted input is incorporated into SQL statements without appropriate safeguards, an attacker could manipulate queries or access sensitive records. Recommended mitigations include parameterized queries, safe database access methods, input validation, and least-privilege database permissions. This is a potential threat identified by TMT, not a confirmed Immich vulnerability. The implementation must be reviewed before determining whether existing controls adequately mitigate this risk.

41. Potential Excessive Resource Consumption for Immich Server (Authentication) or PostgreSQL (Users & Sessions)  [State: Not Started]  [Priority: High] 

Category:Denial Of Service
Description:Does Immich Server (Authentication) or PostgreSQL (Users & Sessions) take explicit steps to control resource consumption? Resource consumption attacks can be hard to deal with, and there are times that it makes sense to let the OS do the job. Be careful that your resource requests don't deadlock, and that they do timeout.
Justification:Authentication and session database operations may consume excessive application or database resources if requests are not appropriately controlled. Repeated or resource-intensive requests could reduce availability for legitimate studio employees. Recommended mitigations include request rate limiting, connection pooling, resource limits, query and connection timeouts, and monitoring for abnormal activity. The implementation and deployment configuration must be reviewed to determine which protections are present. This is a potential availability threat, not a confirmed Immich vulnerability.
